# MVP: MyShop — creator-commerce для России (дизайн)

Дата: 2026-09-09

## Контекст и цель

MyShop — платформа creator-commerce по модели ShopMy: связывает блогеров
("creators") и магазины/бренды через партнёрские ссылки. Целевые вертикали
на старте: косметика, мужские товары, одежда — без разделения по отдельным
подпродуктам, единая витрина с тегами категорий.

Цель MVP — проверить самую рискованную гипотезу: **будут ли блогеры вообще
создавать у себя витрину и делиться обёрнутыми ссылками**, прежде чем
вкладываться в интеграции с партнёрками WB/Ozon/CPA-сетями, начисление
комиссий и брендовый кабинет.

## Кто первый пользователь

Creators (блогеры/кураторы). Магазины/бренды и реальная монетизация —
вне скоупа MVP.

## Что входит в MVP

- Регистрация/логин creator'а (Supabase Auth, email/пароль)
- Личный кабинет creator'а: добавление товара вручную (произвольная
  ссылка, название, фото по URL, цена, категория)
- Публичная страница-витрина creator'а по slug
- Обёрнутая ссылка на каждый товар, которая логирует клик и делает
  редирект на оригинальный URL
- Счётчик кликов в кабинете creator'а

## Что не входит в MVP (сознательно)

- Интеграция с партнёрскими API WB/Ozon/CPA-сетей
- Начисление и трекинг комиссий, выплаты creator'ам
- Кабинет для брендов/магазинов
- Telegram-бот, браузерное расширение
- Разделение UI по вертикалям (косметика/мужское/одежда) — на старте это
  просто тег на товаре, не отдельные разделы продукта

Обоснование: пока не подтверждено, что creators готовы заводить у себя
витрину и активно делиться ссылками, любая интеграция с партнёрками —
преждевременная инвестиция.

## Архитектура

Одно Next.js-приложение (TypeScript), без отдельных сервисов.

Редирект и трекинг кликов реализованы как Route Handler внутри того же
приложения (`/r/[linkId]`), а не как отдельный edge-сервис — при объёме
кликов MVP отдельная инфраструктура для редиректов не нужна и добавляет
сложность без пользы на этом этапе. Если редиректы станут узким местом,
их можно вынести в отдельный сервис позже без изменения модели данных.

## Роуты

- `/` — публичный лендинг
- `/signup`, `/login` — аутентификация через Supabase Auth
- `/dashboard` — кабинет creator'а: список товаров, форма добавления,
  клики по каждой ссылке
- `/[creatorSlug]` — публичная витрина creator'а (карточки товаров)
- `/r/[linkId]` — редирект-роут: пишет клик (timestamp, referrer,
  user-agent) в БД, затем делает 302 на `target_url`

## Модель данных (Postgres / Supabase)

```
creators
  id            uuid PK
  user_id       uuid FK -> auth.users
  slug          text unique
  display_name  text
  bio           text nullable
  created_at    timestamptz

links
  id            uuid PK
  creator_id    uuid FK -> creators.id
  title         text
  image_url     text nullable
  price         numeric nullable
  category      text        -- 'cosmetics' | 'mens' | 'clothing' | ...
  target_url    text
  created_at    timestamptz

clicks
  id            uuid PK
  link_id       uuid FK -> links.id
  clicked_at    timestamptz
  referrer      text nullable
  user_agent    text nullable
```

Row Level Security: creator видит и редактирует только свои `links`;
`clicks` доступны на чтение только владельцу связанного `link` (через
`creator_id`). Публичная витрина (`/[creatorSlug]`) читает `links` без
авторизации (публичные данные), запись в `clicks` разрешена анонимно
только через сам redirect-роут (server-side, не напрямую из браузера).

## Тестирование

- Ручная проверка полного пути: регистрация → добавление товара →
  переход по `/r/[linkId]` → клик виден в `/dashboard`
- Unit-тесты на логику редиректа (валидный/невалидный `linkId`, запись
  клика, корректный 302 на `target_url`)
- Unit-тесты на RLS-сценарий (creator не видит чужие links/clicks) —
  через Supabase test client
